## О проекте

`routerus` — интерактивный bash-скрипт, который на чистой Ubuntu 24.04
разворачивает готовую к работе VPN-ноду для [Remnawave Panel](https://github.com/remnawave/panel):
хардит систему, поднимает [Xray-core](https://github.com/XTLS/Xray-core) с
VLESS + Reality, маскирует ноду под легитимный сайт и печатает готовый JSON для
вставки в панель. Одна нода — один домен.

Скрипт **идемпотентен**: повторный запуск не ломает уже настроенную ноду, а на
живой ноде пропускает `apt upgrade`, чтобы не оборвать трафик.

В репозитории три скрипта:

| Скрипт                | Что делает                                              |
|-----------------------|---------------------------------------------------------|
| `deploy-remnanode.sh` | разворачивает новую ноду с нуля                          |
| `update-node.sh`      | накатывает правки на **уже развёрнутую** ноду            |
| `check-node.sh`       | read-only диагностика: ничего не меняет, только проверяет |

## Возможности

- **VLESS + Reality** — TLS-маскировка без собственного сертификата; DPI и
  пробберы видят легитимный TLS-хендшейк.
- **Три режима транспорта** — выбор цифрой `1`/`2`/`3` при запуске (Enter = `1`):
  - `1` `tcp` (по умолчанию) — RAW + `xtls-rprx-vision`, полная совместимость с
    любым клиентом, включая podkop/Nikki на mihomo;
  - `2` `xhttp` — `mode=packet-up`: дробит upload под API-запросы, устойчив к
    поведенческому DPI на мобильных сетях РФ;
  - `3` `both` — оба inbound на одной ноде (`tcp:443` + `xhttp:<port>`) с общим
    `privateKey`; подписка отдаёт обе ссылки, podkop берёт tcp.
- **steal_oneself** — Reality `dest` указывает на собственный nginx на том же
  сервере: SNI резолвится на наш IP → настоящий сайт → всё легитимно.
- **Фейковый сайт** — генератор бизнес-лендинга, детерминированный от хэша
  домена: на ре-запуске не меняется (фингерпринт стабилен), но между нодами
  различается не только палитрой — именами CSS-классов, числом и порядком
  секций, шрифтом, форматированием стилей. Плюс `about.html`, `404.html`,
  `robots.txt` и `favicon.ico`.
- **Изоляция от внутренней сети** — приватные диапазоны (cloud-metadata
  `169.254/16`, RFC1918, loopback) в Config Profile идут в `BLOCK`. Нода не
  пойдёт по адресу, который ей назвал клиент, — ни в metadata хостера, ни в
  собственный API в обход UFW.
- **Хардинг из коробки** — SSH key-only на **случайном порту** (константа на
  весь флот была маркером для сканеров), `ssh.socket` замаскирован, fail2ban,
  sysctl (BBR, TCP-буферы, SYN-flood protection), UFW, автообновления
  безопасности. Управляющие порты открыты только своим IP, не всему интернету.
- **Docker из подписанного репозитория** — установка через официальный apt-репо
  с GPG-проверкой пакетов, а не `curl … | sh`; заодно гарантирует
  `docker compose` v2.
- **Безопасность секретов** — приватный ключ Reality не попадает в лог (Config
  Profile пишется в `config-profile.json` `600` и на терминал); лог, `.env` и
  `keys.txt` с правами `600`, фейк-сайт `644` (иначе nginx отдал бы 403).
- **Zero-downtime SSL** — выпуск и продление через webroot, nginx не гасится;
  renewal-hook пересоздаёт контейнер ноды, чтобы Xray подхватил новый сертификат.
- **Watchdog реального inbound** — проверяется коннект на `443` (и на xhttp-порт
  в режиме `both`), а не факт существования контейнера. Отказ «контейнер жив,
  панель зелёная, Xray мёртв» ловится, а не приходит от клиентов.
- **Эксплуатация** — ротация docker-логов и логов ноды, опциональный агент
  [Beszel](https://github.com/henrygd/beszel).

## Быстрый старт

### 1. Домен

Купи домен (`.ru` от 129 ₽/год) и настрой DNS A-запись на IP сервера.

### 2. Запуск

```bash
ssh root@IP_СЕРВЕРА
bash <(wget -qO- https://raw.githubusercontent.com/anfixit/routerus/main/deploy-remnanode.sh)
```

Скрипт спросит: **домен**, **публичный SSH-ключ**, **имя ноды**, **IP панели
Remnawave**, **транспорт**. Для ключа он печатает команды получения `.pub` под
macOS/Linux (`cat ~/.ssh/id_ed25519.pub`) и Windows
(`Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub` в PowerShell,
`type %USERPROFILE%\.ssh\id_ed25519.pub` в cmd). Транспорт выбирается цифрой
`1`/`2`/`3` (Enter = `1`/tcp); для `both` дополнительно спрашивается порт xhttp.

> **IP панели** нужен, чтобы UFW пускал к API ноды (`2222`) только её. Ответ
> `any` оставит порт открытым всему интернету — так делать не стоит, открытый
> `2222` с характерным TLS-ответом Remnawave выдаёт весь флот сканом IPv4.
> При смене IP панели нода отвалится от **управления**, но VPN продолжит
> работать: Xray живёт своим конфигом. Правится на ноде одной командой —
> `ufw allow from НОВЫЙ_IP to any port 2222 proto tcp`.

> **SSH-порт случайный на каждую ноду** — но это предложение, а не приговор:
> скрипт показывает выбранный порт и даёт задать свой (Enter — принять). Это
> важно, если у хостера есть внешний файрвол (security group), где высокие
> порты закрыты снаружи. Порт вносится в UFW **до** рестарта sshd, а не в
> фазе 14, иначе проверка доступа провалилась бы из-за файрвола.
>
> После фазы 3 скрипт останавливается и ждёт подтверждения доступа из другого
> терминала — так опечатка в ключе или закрытый порт обнаруживаются, пока
> текущая сессия ещё жива. Если доступ не подтверждается, скрипт предложит
> откатить хардинг SSH на прежние настройки. Порт печатается в итоговой сводке
> и сохраняется в `/opt/remnanode/node-info.txt`; занеси его в свой реестр нод,
> наизусть он больше не угадывается.

Опциональные переменные окружения:

```bash
# пин образа ноды (по умолчанию remnawave/node:latest)
REMNANODE_IMAGE=remnawave/node:2.8.0 bash deploy.sh
# пин образа для генерации ключей (по умолчанию :latest)
XRAY_KEYGEN_IMAGE=ghcr.io/xtls/xray-core:26.6.27 bash deploy.sh
# email для Let's Encrypt (по умолчанию регистрация без email)
CERTBOT_EMAIL=you@example.com bash deploy.sh
# резолвер в Config Profile (по умолчанию нефильтрующий Cloudflare DoH)
DNS_SERVER=https://dns.quad9.net/dns-query bash deploy.sh
# таймзона ноды (по умолчанию Europe/Moscow)
NODE_TZ=UTC bash deploy.sh
```

### 3. Настройка в панели

Скрипт печатает готовый JSON и пошаговый чек-лист (см.
[ниже](#настройка-в-панели-remnawave)). После ввода `SECRET_KEY` из панели
контейнер поднимается автоматически.

### 4. Проверка

Доступ по SSH скрипт заставит проверить сам — на фазе 3, не отпуская текущую
сессию. После завершения остаётся проверить ноду целиком:

```bash
sudo bash check-node.sh
```

Скрипт read-only: смотрит реальный inbound, цепочки fail2ban, правила UFW, срок
сертификата, watchdog и права на секреты. Ничего не меняет. Коды выхода:
`0` — чисто, `2` — есть предупреждения, `1` — есть отказы.

## Как это работает

```
Клиент (Happ / v2rayNG / podkop-Nikki на mihomo)
    │
    ▼
Xray :443  (VLESS + Reality + TCP/Vision | XHTTP)   [+ xhttp:<port> в режиме both]
    │
    ├── Reality-клиент ──────────► VPN-туннель ──► интернет
    │
    └── Не-Reality (DPI / проббер)
            │
            ▼
        nginx :8443  (настоящий сайт с SSL)  ← steal_oneself
```

Reality проверяет клиента по x25519-ключу и shortId. Легитимный трафик уходит в
туннель; всё остальное (DPI-зонды, случайные боты) Reality прозрачно
проксирует на локальный nginx с настоящим сайтом — сервер выглядит как обычный
веб-хостинг.

### Фазы установки

Скрипт выполняет 17 фаз (0–16): проверки окружения (включая свободный :443) →
ввод параметров → зависимости и Docker (подписанный apt-репо) → хардинг SSH с
паузой на подтверждение доступа → fail2ban → sysctl и таймзона → nginx :80 + SSL
(webroot) → nginx-fallback :8443 → фейковый сайт → генерация ключей и JSON →
пауза на настройку панели → запуск `remnawave-node` → автообслуживание →
watchdog → UFW → Beszel → итоговая сводка.

### Открываемые порты

| Порт      | Доступен кому            | Назначение                             |
|-----------|--------------------------|----------------------------------------|
| случайный | всем                     | SSH (key-only), свой на каждой ноде    |
| 443       | всем                     | Xray Reality (VLESS tcp/xhttp)         |
| `<port>`  | всем                     | Xray Reality XHTTP (только режим both) |
| 80        | всем                     | HTTP-редирект + ACME challenge         |
| 2222      | **только IP панели**     | Remnawave node API                     |
| 45876     | **только IP хаба**       | Beszel agent (опционально)             |

> nginx-fallback слушает `127.0.0.1:8443` (только loopback — через него ходит
> Reality), наружу не публикуется.

Управляющие порты (`2222`, `45876`) намеренно не открыты всему интернету.
Открытый `2222` отвечает характерным для Remnawave TLS-хендшейком, то есть
служит меткой: найдя одну ноду, остальные можно собрать одним запросом в
Censys или Shodan. То же для Beszel на `45876`. Ограничение по источнику
снимает оба признака и ничего не стоит в эксплуатации.

## Настройка в панели Remnawave

> Актуально для Panel 2.8.0. Учти изменения хостов в этой версии: единый `tag`
> заменён на массив `tags[]`; `allowInsecure` убран; фиксированные значения
> `fingerprint` больше не enum — это свободная строка (`chrome` по-прежнему
> валиден); ALPN поддерживает `h2`, `h3` и комбинации.

1. **Config Profiles → Create** — вставить JSON из вывода скрипта.
2. **Nodes → Create** — Address = IP сервера, Port `2222`, привязать профиль,
   включить все inbound, скопировать `SECRET_KEY` обратно в скрипт.
3. **Hosts → Create** — Address и SNI = домен, Fingerprint `chrome`.
   **Хост создаётся на каждый inbound отдельно**, один хост на два inbound не
   работает: подписка отдаёт по ссылке на хост.
   - `tcp`-хост: Port `443`, ALPN не задавать, Flow не задавать — для
     VLESS + Reality + TCP панель подставит `xtls-rprx-vision` сама;
   - `xhttp`-хост: Port `443` (или `<port>` в режиме `both`), ALPN `h2`,
     Path `/api/v1/update`, Mode `packet-up`;
   - в режиме `both` хостов **два**.
4. **Internal Squads → Default-Squad** — добавить все inbound ноды
   (без этого нода не попадёт в подписку).

> Скрипт печатает этот чек-лист с уже подставленными доменом, IP, именами
> inbound и портами — и сохраняет его в `/opt/remnanode/panel-setup.txt`,
> чтобы не выуживать из прокрутившегося терминала:
> ```bash
> cat /opt/remnanode/panel-setup.txt
> ```

> Проверь готовую ссылку подписки: для tcp-инбаунда в ней должно быть
> `&flow=xtls-rprx-vision`. Если flow не появился — в Config Profile поменяй
> `"network": "tcp"` на `"network": "raw"` (в Xray 26.x это одно и то же).

## Клиент и селективная маршрутизация

TCP + Vision выбран по умолчанию ради маршрутизации на роутере: ядро mihomo
(podkop / Nikki) парсит ссылку подписки Remnawave с `flow=xtls-rprx-vision`
без доработок.

> **Начиная с Panel/Node 2.8.0** Remnawave умеет генерировать XHTTP- и
> Hysteria2-подписки и для клиентов на ядре **Mihomo** (полный набор xmux,
> download-settings и padding). Если твоя сборка podkop собрана со свежим
> mihomo — XHTTP на роутере становится реально применим; проверяй на своей
> прошивке перед раскаткой на флот.

В режиме `both` подписка содержит и tcp-, и xhttp-ссылку — приложения (Happ)
видят обе, а роутер берёт tcp. Раскатка подписки на роутер и авто-выбор
быстрейшего сервера живут в отдельных инструментах (`podkop-sub`, `fleet_deploy`)
и в этот репозиторий не входят.

## Обслуживание флота

Часть правок нужна на **уже развёрнутых** нодах, а не только при новом деплое.
Для этого есть `update-node.sh` — идемпотентный, без пересоздания контейнера:

```bash
sudo PANEL_IP=1.2.3.4 bash update-node.sh
```

Что делает: заменяет watchdog на проверку реального inbound, снимает ночной
geo-крон, ограничивает `2222`/`45876` по источнику, восстанавливает цепочки
fail2ban, выставляет таймзону, закрепляет `nf_conntrack_max`, включает
logrotate, чинит права на секреты. Чего **не** трогает: ключи Reality,
`SECRET_KEY`, домен, сертификаты, SSH-порт, образ ноды и `docker-compose.yml`.

Сначала посмотреть, что он собирается сделать:

```bash
sudo PANEL_IP=1.2.3.4 DRY_RUN=1 bash update-node.sh
```

> **Две правки живут в панели, а не на ноде**, и скрипт их сделать не может —
> он только проверит локальную копию профиля и напомнит:
> в `routing.rules` приватные сети должны идти в `BLOCK`, а не в `DIRECT`
> (`domainStrategy: IPIfNonMatch` при этом **оставить** — именно он резолвит
> домен перед проверкой IP-правил); в каждом inbound нужен
> `"sniffing": {"enabled": true, "destOverride": ["http","tls"], "routeOnly": true}`.

Состояние ноды в любой момент:

```bash
sudo bash check-node.sh
```

## Обновление нод

Ядро Xray живёт **внутри** docker-образа `remnawave/node`, а Reality-конфиг
хранится в панели, не на ноде. Поэтому при выходе новой версии ядра
(например, Node 2.8.0 → Xray-core 26.6.27) **полная пересборка не нужна** —
достаточно подтянуть свежий образ. Хардинг, nginx, SSH и ключи не затрагиваются.

```bash
cd /opt/remnanode && docker compose pull && docker compose up -d
```

Чтобы зафиксировать конкретную версию, поправь строку `image:` в
`/opt/remnanode/docker-compose.yml`. Ре-запуск `deploy-remnanode.sh` **сохранит
твой тег**: если переменная `REMNANODE_IMAGE` не задана явно, скрипт читает
текущее значение из существующего compose. А если образ не пинован
(`:latest`), он спросит подтверждение перед `pull` — молча апгрейдить ядро на
живой ноде он не станет.

> Панель мониторит только API-порт `2222` — нода может показываться «зелёной»
> при мёртвом VPN-инбаунде. Начиная с v3.10 этот случай ловит watchdog, но
> после ручного обновления стоит проверить самому: `sudo bash check-node.sh`.

## Эксплуатация

| Задача                    | Где                                            |
|---------------------------|------------------------------------------------|
| Ключи Reality и shortId   | `/opt/remnanode/keys.txt` (chmod 600)          |
| Параметры ноды, SSH-порт  | `/opt/remnanode/node-info.txt` (chmod 600)     |
| Лог установки             | `/var/log/deploy-remnanode.log` (chmod 600)    |
| Проверка inbound          | cron `*/5` → `watchdog.sh`, лог `/var/log/watchdog.log` |
| Диагностика ноды          | `sudo bash check-node.sh`                      |
| Накатка правок на ноду    | `sudo PANEL_IP=… bash update-node.sh`          |
| Обновление образа ноды    | `docker compose pull && up -d` в `/opt/remnanode` |
| Логи ноды                 | `docker logs remnawave-node`                    |

> **Геофайлы больше не скачиваются и не обновляются по крону.** Единственным их
> потребителем было правило `geoip:private`, теперь заданное явным списком CIDR;
> `geosite`-правил в конфиге нет, а образ ноды несёт собственные `.dat`. Раньше
> `runetfreedom` публиковал обновления почти ежедневно, `cmp` видел разницу и
> запускал `--force-recreate` — то есть каждую ночь и одновременно на всём флоте
> рвались все активные соединения.

## Безопасность

- **Приватные сети недостижимы через ноду.** Cloud-metadata (`169.254.0.0/16`),
  RFC1918, loopback и прочие служебные диапазоны идут в `BLOCK` первым правилом
  роутинга. Без этого клиент мог указать в VLESS-заголовке `169.254.169.254` и
  прочитать `user-data` виртуалки, просканировать внутреннюю сеть хостера или
  постучаться в собственный API ноды на `127.0.0.1:2222` в обход UFW — коннект
  инициируется самой нодой, поэтому файрвол его не видит.
- **Управляющие порты закрыты по источнику** — `2222` доступен только панели,
  `45876` только хабу Beszel.
- Приватный ключ Reality печатается только на терминал; Config Profile с ключом
  сохраняется в `/opt/remnanode/config-profile.json` (`600`) и не пишется в лог.
- Лог установки, `.env`, `keys.txt` и `node-info.txt` создаются с правами `600`;
  фейк-сайт — `644` (иначе nginx-воркер отдаёт 403 и ломает маскировку).
- SSH: только по ключу, root запрещён, случайный порт на ноду, `ssh.socket`
  замаскирован, `sshd -t` перед рестартом и `sshd -T` после (проверяется не
  синтаксис, а какое значение реально победило в склейке дроп-инов), пауза на
  подтверждение доступа до продолжения, fail2ban. Существующие ключи в
  `authorized_keys` дополняются, а не затираются.
- Цепочки fail2ban пересоздаются после `ufw`: reset файрвола перестраивает
  filter-таблицу без `f2b-*`, и джейл продолжает рапортовать «enabled», не имея
  ни одного правила в `iptables`.
- SSL выпускается и продлевается через webroot без остановки nginx; проверяется
  срок сертификата, а не факт наличия каталога. Продление пересоздаёт контейнер
  ноды (renewal-hook), чтобы Xray подхватил новый cert.
- Docker ставится из официального apt-репозитория с GPG-проверкой пакетов
  (не `curl … | sh`); проверяется наличие `docker compose` v2. `daemon.json`
  дополняется через `jq`, а не перезаписывается, и демон рестартует только при
  реальном изменении конфига.
- Существующие `daemon.json` / `sshd_config` / `compose` / `keys.txt`
  резервируются перед перезаписью.

### Приватность DNS

Резолвер в Config Profile по умолчанию **нефильтрующий** (`https://1.1.1.1/dns-query`).
Это осознанный выбор: при `domainStrategy: IPIfNonMatch` через него проходят
доменные запросы всех клиентов, и передача их фильтрующему стороннему сервису
была бы фактом, который придётся раскрывать в Политике конфиденциальности.
Плюс фильтрующие резолверы ломают краш-репортинг и A/B-конфиги мобильных
приложений — пользователь приходит в поддержку с «у вас приложение не
работает» и связь с VPN не строит.

Блокировка рекламы и трекеров осталась в `routing` по доменам — она от
резолвера не зависит. Сменить резолвер можно переменной `DNS_SERVER`.
Если ставишь фильтрующий — задекларируй это в Политике конфиденциальности.

Нашёл проблему безопасности? Не открывай публичный issue — см.
[SECURITY.md](SECURITY.md).

## FAQ

**Почему TCP по умолчанию, а не XHTTP?**
TCP + Vision совместим со всеми клиентами и стабилен. XHTTP (`packet-up`)
устойчивее к поведенческому DPI на мобильных сетях, но с частью клиентов на
mihomo исторически менее надёжен — хотя в Panel 2.8.0 поддержка Mihomo+XHTTP
уже появилась. Выбор остаётся за тобой при запуске.

**Зачем режим `both`?**
Одна нода отдаёт и tcp (для podkop/флота), и xhttp (для клиентов за жёстким
DPI) одновременно, с общим ключом.

**Не нашёл поле Flow в панели.**
Его там и нет. Remnawave добавляет `flow: xtls-rprx-vision` автоматически для
VLESS + Reality + TCP. Проверить можно в готовой ссылке подписки.

**Обновилось ядро — надо пересобирать ноды?**
Нет. Ядро внутри docker-образа. На ноде: `cd /opt/remnanode && docker compose
pull && docker compose up -d`. Reality-конфиг, ключи и хардинг не тронутся.

**Можно ли запускать deploy повторно?**
Да, скрипт идемпотентен: пользователь, SSH-порт, ключи Reality и shortId,
`SECRET_KEY`, тег образа и правила UFW переиспользуются, `apt upgrade` на живой
ноде пропускается. Config Profile при ре-запуске получается **тот же самый** —
до v3.10 ключи перегенерировались, и оператор, следуя инструкции фазы 10,
вставлял в панель новый профиль, мгновенно отключая всех клиентов ноды.

**Я потеряла SSH-порт ноды.**
Он в `/opt/remnanode/node-info.txt` на самой ноде и в итоговой сводке в
`/var/log/deploy-remnanode.log`. Если доступа нет совсем — только консоль
хостера: `grep Port /etc/ssh/sshd_config.d/00-hardening.conf`.

**Зачем случайный SSH-порт, если это не защита?**
Это не защита от взлома, а снижение корреляции. Одинаковый нестандартный порт
на всех нодах — редкое сочетание, по которому флот собирается одним поиском.
Отдельно взятой ноде случайный порт не добавляет стойкости.

**Нода не появилась в клиенте.**
Проверь шаг 4 в панели — inbound должен быть добавлен в Internal Squad, иначе он
не попадёт в подписку.

**Работает на одном устройстве, не работает на другом.**
Первым делом — **обнови подписку вручную в каждом клиенте**, а не жди
автообновления. Клиент кеширует ссылки и перечитывает их по своему расписанию,
поэтому после правки в панели устройства подхватывают исправление в разное
время. Разница «на телефоне работает, на компьютере нет» почти всегда означает
именно это, а не проблему сети: сначала обнови подписку везде и только потом
делай выводы.

Если после обновления подписки на всех устройствах разница осталась и зависит
от сети (мобильный интернет против Wi-Fi) — тогда это уже похоже на блокировку
у провайдера. TCP + Vision на стандартном `443` имеет характерный профиль
трафика, и часть операторов его режет, тогда как XHTTP на нестандартном порту
выглядит как обычные HTTP-запросы. Ради этого и существует режим `both`: там,
где один транспорт заблокирован, работает второй. Нужен именно TCP на
проблемной сети — перенеси его inbound на нестандартный порт (например `2053`),
открой порт в UFW и **пересоздай хост** в панели.

**Половина ссылок ноды работает, половина нет.**
Почти всегда причина в панели, а не на ноде. Проверь по порядку:
1. `sudo bash check-node.sh` — если он чист, нода исправна;
2. `pbk=` в ссылке подписки должен совпадать с `PUBLIC_KEY` из
   `/opt/remnanode/keys.txt`. Не совпал — хост привязан к устаревшей записи
   инбаунда, пересоздай хост;
3. у каждого хоста должен быть задан **Fingerprint** (`chrome`): без него
   Reality не признаёт клиента и молча отдаёт его на фейк-сайт;
4. если правил Config Profile — **пересоздай все хосты этой ноды**: они
   сохраняют параметры на момент создания и после правки профиля устаревают.

**Нода перестала быть зелёной сразу после обновления.**
Скорее всего, неверно указан IP панели и UFW отрезал `2222`. VPN при этом
работает. Проверь `sudo ufw status | grep 2222`; временно вернуть доступ —
`sudo ufw allow 2222/tcp`.

## Вклад

PR и issue приветствуются. Перед отправкой:

- прогони [ShellCheck](https://www.shellcheck.net/) по всем трём скриптам —
  должно быть без замечаний:
  ```bash
  shellcheck -s bash deploy-remnanode.sh update-node.sh check-node.sh
  ```
- проверь синтаксис: `bash -n deploy-remnanode.sh`;
- сохраняй идемпотентность и не пиши секреты в лог;
- держи стиль: фазовые функции, хелперы `ok/info/warn/die`, `set -Eeuo pipefail`
  (именно `-E`: без `errtrace` ERR-trap не наследуется функциями, а весь код
  живёт в `phaseN_*`).
